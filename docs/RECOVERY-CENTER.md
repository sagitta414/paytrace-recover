# Recovery Center: setup, behavior and verification

The Recovery Center is available at `/recovery.html` from the Recovery pulse and footer. These features extend the existing sandbox prototype; they do not turn it into a production payment or identity system.

## Delivered features

1. **Analytics and reporting:** UTC creation-date filters (up to 366 days), sample/provider filters, current recovery rates, unresolved cases, latest failed verification counts, average opened-to-latest-passing-check time, daily cohorts, accessible data tables and formula-safe CSV reports. Currency totals remain separate. Outstanding access value represents paid purchases without verified access; it is not unpaid debt, incremental revenue or money collected.
2. **Automated follow-ups:** durable internal tasks, customer-response-aware follow-ups and manager escalations. Disabled by default. Minimum 24-hour cooldown, 1–5 lifetime automated follow-ups per case, skip verified cases and running recovery jobs. Customer responses pause automated email. Email needs a separate explicit checkbox plus configured Resend delivery and a case contact. Disabling automation/email cancels unsent automatic mail. Tasks never approve, charge or grant access. The running Node service checks every 30 seconds; this is not an external scheduler when the service is stopped.
3. **Audit logs:** workspace-scoped successful and denied access, case action names, team changes and workflow stages. Search, pagination and JSON checkpoint export. Entries chain hashes and keep a separate head to detect edits or deleted tail entries. Set a stable external `AUDIT_HMAC_KEY` (32+ characters) for HMAC protection. With no key the UI explicitly says Unkeyed. Keep checkpoints outside the database to detect rollback; this is not immutable/WORM storage. Never change or lose a configured key without a migration plan. Existing entries start with this update; earlier history cannot be reconstructed.
4. **Roles:** Admin (workspace owner), Manager, Analyst and Read-Only. Server checks every API request, including crafted requests. Managers can access customer information, approve repairs and use payment controls; Analysts can investigate redacted cases; Read-Only can view redacted reports/receipts. Only the owner Admin can issue expiring bearer access links, after unlocking the operator session. Links expire in 1–168 hours and can be revoked immediately. Labels identify issued access, not verified personal identities. Production authentication, SSO/MFA, tenant administration and identity verification still need implementation before a merchant launch.
5. **PayPal integration:** existing sandbox checkout and idempotent capture now include `POST /api/webhooks/paypal`, signature verification through PayPal's official verification endpoint, durable event ID/digest deduplication, retryable processing and authoritative read-only reconciliation. A webhook never trusts its payload to grant access. Supported capture events: completed, pending, denied, refunded and reversed. Unknown events are acknowledged without mutation. No raw webhook payment payload or card data is persisted. PayPal sandbox is the supported provider; Stripe and production payments are not included.
6. **History:** case evidence, approval and verification events, audit mutations, outreach metadata and delivery states. Private messages, addresses and notes remain in the restricted communication desk. The earlier core event list is bounded; audit tracking persists new actions and the center shows the latest 200 case audit mutations. Full audit history has pagination.
7. **Notifications:** overdue paid access (configured delivery window), customer responses, due internal reminders, failed verification, required approval and escalations. Persistent deduplication and shared workspace read markers; resolved conditions leave the active list. Notifications refresh on demand and background checks, without browser push permission or external alerts to staff.
8. **AI prioritization:** explainable age/value/status rules with an optional explicit AI second look using the configured Responses model. Only case IDs, age, value, currency, status and rule explanations are sent. Output must contain each known case once; invalid/duplicate IDs and incomplete outputs are rejected. AI suggestions do not save priorities, approve repairs or send messages. Different currencies are not converted.
9. **Recovery Receipt & Verification Center:** current verification state, source label, exact approval role/time, provider status, access-grant count, content checks, audit integrity/checkpoint, JSON download and print view. Sample receipts always say Illustrative sample. A passing receipt is not a guarantee of future access or customer confirmation.

## Configuration

Use Node 24 or newer. Run `npm ci`, `npm test`, `npm start`; open `http://127.0.0.1:4358/recovery.html`. Set PORT and PUBLIC_URL together for a different port. The development review instance uses 4360. The static simulation remains on 4357 and does not issue team access or backend audit records.

Existing optional credentials stay server-side in `.env` or hosting secrets. Set `DEMO_OPERATOR_KEY` to unlock owner integrations/team invitations. Add `AUDIT_HMAC_KEY` for keyed audit integrity. Generate a random value locally with `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"` and save it only in server secrets. Do not commit the generated value.

Register an HTTPS sandbox webhook URL ending in `/api/webhooks/paypal` in the same PayPal app as your credentials. Subscribe to supported capture events and set its ID as `PAYPAL_WEBHOOK_ID`. The server posts signed headers, webhook ID and event to PayPal's verification endpoint. No certificate URL is fetched by this app. Reconciliation uses current PayPal GET reads and invalidates stale approvals/proof. Complete a sandbox checkout and test valid, invalid, duplicate, refunded and reversed events against your configured account before deployment. Provider reads never recapture a payment.

Official verification reference: https://developer.paypal.com/api/webhooks/v1/#verify-webhook-signature

## Validation and remaining setup

128 automated tests pass, including existing recovery invariants and new analytics, roles, forged HTTP requests, revocation/logout, audit editing/deletion/corruption, cooldown/caps/transaction rollback, email cancellation, AI output/privacy validation and webhook signature/deduplication/concurrency/retry/HTTP tests.

Browser verification covered source filters and empty results, receipt downloads, workflow settings, audit search, missing AI configuration, operator-protected reconciliation, desktop/mobile layouts, and an explicit sample review → preview → approval → one grant → authenticated content verification. The receipt and analytics updated to one verified case. No browser console errors were recorded.

Live PayPal, OpenAI, Render and email credentials were not supplied, so live acceptance is not claimed. SQLite and in-process locks target a single Node service instance. Shared transactional storage, production authentication, retention/archival, monitoring, and an external scheduler are required for production scale. Keep credentials, `.env`, databases, issued team links and runtime logs out of commits and source packages.
