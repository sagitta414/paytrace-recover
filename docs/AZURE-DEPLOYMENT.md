# Azure demo deployment

The Node demo is hosted at `https://paytrace-recover-sagitta.azurewebsites.net/` on the existing Linux Basic B1 App Service plan `provenance-broker-plan` in resource group `provenance-pilot-rg`. It shares that plan's capacity with other apps. The attempted dedicated free F1 plan was rejected because this subscription has zero F1 VM quota; it was not created. The empty resource group from that attempt was removed.

The app uses Node 24 LTS, `npm start`, Always On, and `/home/data/courselatch.sqlite` for the single-instance demo database. Keep the app at one instance: SQLite and the in-process lock are not suitable for scale-out. The public Sites URL remains a browser simulation; the Azure URL serves the Node backend. Start a review at `/judge.html` to distinguish those paths.

## Connected sandbox setup

All provider settings belong in Azure App Service **Environment variables**, never in source or browser code. `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, and `PAYPAL_WEBHOOK_ID` still need to be copied from the same sandbox app. Add `https://paytrace-recover-sagitta.azurewebsites.net/api/paypal/webhook` as a `PAYMENT.CAPTURE.COMPLETED` webhook in the PayPal developer dashboard. The separate reference course service is deployed at `https://paytrace-course-sagitta.azurewebsites.net` and its URL and private key are configured in the PayTrace Azure app. It implements [the contract](COURSE-ACCESS.md); it is a demo service, not a commercial LMS connector. The Azure app already has a generated `DEMO_OPERATOR_KEY`; view or rotate it in App Service settings when you need to unlock a demo browser session. Do not share it in a public screenshot.

The four specialist roles use the existing Azure OpenAI `gpt-4o-mini` deployment on `automation-jl107`. The Azure App Service has `OPENAI_BASE_URL=https://automation-jl107.openai.azure.com/openai/v1/`, `OPENAI_MODEL=gpt-4o-mini`, and a server-side `OPENAI_API_KEY` configured. The four-call-role consultation was confirmed against the live Azure model on 2026-10-24. A local `npm run ai:smoke` check runs all four specialists against fictional evidence and reports the outcome without a repair. Prism can hold a case for more evidence; a model consultation alone does not establish a connected PayPal recovery.

To use Render Workflows while the web app is on Azure, create a Render Blueprint from `render-workflow.yaml`, or create the Workflow service manually. The Blueprint contains only the workflow service; the root `render.yaml` would provision an additional web app. Set `WORKFLOW_SECRET`, `RENDER_API_KEY`, `RENDER_INVESTIGATE_TASK`, and `RENDER_RECOVER_TASK` on the Azure web app. Configure the same `WORKFLOW_SECRET` and `APP_URL=https://paytrace-recover-sagitta.azurewebsites.net` on Render. No Render Workflow has been created yet. Optional customer email requires `RESEND_API_KEY` and `EMAIL_FROM` from a verified sender.

## What the automation does

The 30-second monitor rereads **known** sandbox purchases. After the configured 1–60 minute delivery window, an exact completed PayPal capture with missing course access is marked for attention. If an operator session is unlocked and AI credentials are configured, it runs the four-specialist model review automatically and saves progress. Failed reviews are marked for attention and held for five minutes before another automatic attempt. The signed PayPal webhook can trigger the same check sooner.

The merchant can opt into a narrow **automatic recovery policy** on the Connections screen. It is off by default and cannot be enabled until PayPal sandbox, AI, and the separate course service are configured. The policy sets an amount ceiling and daily case cap for the single demo course. A current model-backed review with every objection resolved, a fresh exact capture, a matching learner and inactive entitlement, and a passing preview are required. PayTrace then applies one policy-authorized grant and verifies the protected lesson. Cases outside policy require case-by-case merchant approval. An ambiguous grant is held without an automatic retry; failed lesson verification retries reads only. This policy path currently runs in the Azure server monitor, not Render Workflows.

The monitor also handles a different outcome: the course service may restore access through its own retry before PayTrace grants anything. For a known sandbox purchase with matching active access, PayTrace now rereads PayPal, checks the entitlement and protected lesson, and marks the case verified with **zero writes**. This path is read-only and does not require AI or an unlocked operator session. If the lesson is unavailable, it stays open and schedules another read-only check.

After the merchant approves the exact preview, the existing manual recovery path applies a single idempotent access grant and verifies a protected lesson. Customer progress messages and optional email are queued from state transitions. A provider accepting email is not proof of inbox delivery. The Focus case screen shows the automation trail, while the run report labels connected versus demo evidence.

Unknown PayPal orders are acknowledged without creating cases. An external checkout or LMS must supply a trusted merchant, learner, course, and order mapping before PayTrace can create cases from unknown events. The current Azure app is a demo workspace with a cookie/operator gate, not production merchant authentication or multi-tenant storage.

## Validation

Check `/health`, load `/focus.html`, then complete a sandbox checkout and verify the exact case state. Confirm the webhook event and fresh PayPal capture agree, missing access is detected only after the delivery window, the AI review records its evidence, the correct manual or policy authorization is recorded, the repair is applied once, the lesson probe passes, and the customer tracker shows the new status. Export the run report. Until credentials are added and this run succeeds, do not claim a connected PayPal/AI/Render recovery.
